ساخت یک Tokenizer از صفر

در درس ۰۱ یک نمونه ساده و آموزشی ساختید؛ در این درس همان ایده را به ابزاری جدی‌تر، مقاوم‌تر و نزدیک‌تر به نیازهای واقعی تبدیل می‌کنید.

نوع درس: ساخت و پیاده‌سازی زبان برنامه‌نویسی: Python

اهداف یادگیری

در پایان این درس باید بتوانید:

  • یک BPE Tokenizer نزدیک به سطح Production بسازید که Unicode، نرمال‌سازی Whitespace و Special Tokenها را به‌درستی مدیریت کند.
  • Byte-level fallback را پیاده‌سازی کنید تا Tokenizer بتواند هر ورودی، از جمله Emoji، متن‌های CJK و Code را بدون تولید Unknown Token رمزگذاری کند.
  • با استفاده از Pre-tokenization regex، متن را پیش از اجرای BPE merge در مرزهای مناسب کلمه، عدد، نشانه‌گذاری و Whitespace تقسیم کنید.
  • یک Tokenizer سفارشی را روی Corpus آموزش دهید و Compression Ratio آن را روی متن‌های چندزبانه با tiktoken مقایسه کنید.
  • جایگاه Chat Template را در تبدیل پیام‌های ساخت‌یافته به Token ID درک کنید.
  • تفاوت میان یک پیاده‌سازی آموزشی Python و یک Tokenizer مناسب Production را از نظر سرعت، صحت و قابلیت بازتولید توضیح دهید.

مسئله چیست؟

BPE Tokenizer درس ۰۱ روی متن انگلیسی کار می‌کرد. حالا همان Tokenizer را با متن ژاپنی، Emoji یا Python Code شامل ترکیبی از Tab و Space آزمایش کنید؛ احتمالاً بخشی از فرایند خراب می‌شود یا خروجی نامناسبی می‌دهد.

مشکل از خود الگوریتم BPE نیست؛ مشکل این است که پیاده‌سازی هنوز کامل نیست. یک Tokenizer مناسب Production باید:

  • ورودی را در سطح Byte و مستقل از زبان مدیریت کند؛
  • پیش از تقسیم متن، Unicode را طبق یک سیاست مشخص Normalize کند؛
  • Special Tokenهایی داشته باشد که هرگز شکسته یا با Tokenهای دیگر Merge نشوند؛
  • Pre-tokenization را با Subword splitting ترکیب کند؛
  • قابلیت Encode و Decode قابل‌اعتماد و ترجیحاً برگشت‌پذیر داشته باشد؛
  • آن‌قدر سریع باشد که در Training pipeline به Bottleneck تبدیل نشود؛
  • تنظیمات Vocabulary، Merge rule، Normalization و Special Tokenها را به‌صورت Versioned ذخیره کند تا نتیجه قابل بازتولید باشد.

Vocabulary مدل GPT-2 شامل 50,257 Token است و Llama 3 از Vocabulary با 128,256 Token استفاده می‌کند. برای مدل‌های خانواده GPT-4 نیز معمولاً Tokenizerهایی با Vocabulary در مقیاس حدود 100,000 Token به کار می‌روند؛ بااین‌حال عدد دقیق به مدل و Encoding مورد استفاده وابسته است.

این اعداد متعلق به نمونه‌های آزمایشی کوچک نیستند. Merge tableهای چنین Vocabularyهایی روی حجم بسیار بزرگی از داده آموزش دیده‌اند. افزون بر خود BPE، اجزایی مانند Normalization، Pre-tokenization، مدیریت Special Token و Chat Template formatting هستند که یک Tokenizer محدود به عبارت hello world را از Tokenizerی مناسب داده‌های گسترده اینترنتی جدا می‌کنند.

در این درس قرار است همین اجزا و منطق پشت آن‌ها را بسازید و درک کنید.

مفهوم اصلی

Pipeline کامل

یک Tokenizer مناسب Production صرفاً یک الگوریتم نیست؛ بلکه Pipelineای از چند مرحله است که هر مرحله مسئله متفاوتی را حل می‌کند.

flowchart LR A["Raw Text"] --> B["Normalize"] B --> C["Pre-Tokenize"] C --> D["BPE Merge"] D --> E["Special Tokens"] E --> F["Token IDs"]

نمودار بالا ترتیب مفهومی مراحل را نشان می‌دهد. در پیاده‌سازی واقعی، شناسایی Special Tokenها معمولاً باید پیش از Normalization و BPE انجام شود تا متن دقیق آن‌ها تغییر نکند یا شکسته نشود. سپس بخش‌های عادی متن وارد Pipeline می‌شوند و ID ثابت Special Tokenها در جای مناسب قرار می‌گیرد.

مرحلهکاری که انجام می‌دهددلیل اهمیت
Normalizeاجرای Unicode normalization مانند NFKC و در صورت نیاز Lowercase کردن یا حذف Accentاز ساخته‌شدن Tokenهای متفاوت برای شکل‌های ظاهراً یکسان جلوگیری می‌کند. برای مثال Ligature با کد U+FB01 یعنی ﬁ در NFKC به دو Character یعنی fi تبدیل می‌شود.
Pre-Tokenizeتقسیم متن به Chunkهای کوچک‌تر پیش از اجرای BPEمانع ایجاد Mergeهای نامناسب میان مرز کلمه‌ها می‌شود؛ برای مثال بهتر است the cat به Tokenی مانند e c تبدیل نشود.
BPE Mergeاجرای Merge ruleهای آموخته‌شده روی Byte sequenceهابخش اصلی Compression است و Byteهای خام را به Subword tokenهای پرتکرار تبدیل می‌کند.
Special Tokensتشخیص و درج Tokenهایی مانند [BOS]، [EOS]، [PAD] و Chat markerهااین Tokenها ID ثابت دارند و ساختار ورودی را به مدل اعلام می‌کنند؛ آن‌ها نباید در BPE merge شرکت کنند.
ID Mappingتبدیل نمایش هر Token به Integer IDمدل Neural Network متن را مستقیماً نمی‌بیند؛ ورودی آن دنباله‌ای از Integer IDها است.

ملاحظات Normalization

Normalization همیشه به معنی «بهترکردن» متن نیست؛ بلکه یک تصمیم طراحی است و باید با هدف مدل هماهنگ باشد.

  • NFC شکل‌های Canonical را یکسان می‌کند، اما Compatibility characterها را کمتر تغییر می‌دهد.
  • NFKC تغییرات بیشتری انجام می‌دهد و برای کاهش تنوع نوشتاری مفید است، ولی ممکن است تفاوت‌هایی را که در یک Domain مهم‌اند از بین ببرد.
  • Lowercase کردن برای مدل‌های Uncased مناسب است، اما در Code، نام موجودیت‌ها، شناسه‌ها و بعضی زبان‌ها اطلاعات را از بین می‌برد.
  • حذف Accent می‌تواند Vocabulary را کوچک‌تر کند، ولی ممکن است معنای کلمات یا املای درست نام‌ها را تغییر دهد.
  • تغییر Tab، Newline و چند Space به یک Space برای متن عمومی شاید مفید باشد، اما در Python Code یا داده‌های قالب‌بندی‌شده می‌تواند معنا را عوض کند.

در نتیجه، Normalization باید در زمان Training و Inference دقیقاً یکسان باشد و همراه Tokenizer ذخیره شود.

Byte-level BPE

Tokenizer درس ۰۱ بر مبنای UTF-8 byte کار می‌کرد و این تصمیم درستی بود؛ اما یک نکته مهم باقی می‌ماند: اگر ورودی شامل Byteهایی باشد که به‌تنهایی یک UTF-8 sequence معتبر تشکیل نمی‌دهند، چه اتفاقی می‌افتد؟

Byte-level BPE با درنظرگرفتن هر مقدار ممکن Byte، یعنی اعداد ۰ تا ۲۵۵، به‌عنوان Token پایه این مشکل را حل می‌کند. بنابراین Base vocabulary دقیقاً ۲۵۶ ورودی دارد. در این روش هر داده‌ای، از متن معمولی گرفته تا Binary data یا متن آسیب‌دیده، قابل Tokenize شدن است و نیازی به [UNK] نخواهد بود.

GPT-2 از یک ترفند نمایشی نیز استفاده می‌کند: هر Byte را به یک Unicode character قابل نمایش نگاشت می‌کند تا Vocabulary و Mergeها خواناتر و قابل ذخیره‌سازی در قالب متن باشند. برای نمونه، Byte مربوط به Space یعنی 0x20 در نگاشت GPT-2 با Character Ġ نمایش داده می‌شود. این نگاشت فقط یک نمایش یک‌به‌یک و برگشت‌پذیر است و منطق اصلی BPE به شکل ظاهری Character اهمیت نمی‌دهد.

قدرت اصلی Byte-level BPE این است که می‌تواند همه زبان‌ها را با یک سازوکار واحد پردازش کند. برای مثال:

  • بسیاری از Characterهای چینی در UTF-8 با ۳ Byte نمایش داده می‌شوند.
  • Characterهای ژاپنی معمولاً چندByteای هستند.
  • عربی، Devanagari و Emoji نیز صرفاً Byte sequenceهای متفاوت‌اند.
  • متن Code، Control characterها و ترکیب زبان‌ها نیز با همان Vocabulary پایه قابل نمایش‌اند.

BPE الگوهای پرتکرار را در این Byte sequenceها پیدا می‌کند؛ همان‌طور که در ASCII byteهای متن انگلیسی الگو پیدا می‌کند. اگر یک Character یا کلمه در Training corpus پرتکرار باشد، Merge ruleها ممکن است Byteهای آن را به یک Token یا چند Subword token فشرده تبدیل کنند. اگر ناشناخته باشد، همچنان با Tokenهای پایه Byte قابل نمایش است.

اصل برگشت‌پذیری

برای یک Byte-level Tokenizer انتظار می‌رود رابطه زیر برای ورودی‌های معتبر برقرار باشد:

decoded = tokenizer.decode(tokenizer.encode(text))
assert decoded == text

اگر Normalization فعال باشد، ممکن است خروجی Decode با متن Normalize‌شده برابر باشد، نه الزاماً با متن خام اولیه. بنابراین باید قرارداد encode و decode را روشن کنید و Testهایی برای Unicode، Emoji، RTL text، Newline، Tab و ورودی خالی بنویسید.

Pre-tokenization

پیش از آنکه BPE متن را پردازش کند، بهتر است متن به Chunkهای مناسب تقسیم شود. این کار اجازه نمی‌دهد Merge algorithm از مرزهایی عبور کند که شما از نظر زبانی یا ساختاری نامعتبر می‌دانید.

GPT-2 برای تقسیم متن از Regex زیر استفاده می‌کند:

'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

این Pattern چند نوع قطعه را شناسایی می‌کند:

  • Contractionهای انگلیسی؛ برای مثال don't تقریباً به don و 't تقسیم می‌شود.
  • دنباله Letterها با یک Space اختیاری در ابتدای آن‌ها.
  • دنباله Numberها با Space اختیاری.
  • Punctuation و Symbolهایی که Letter، Number یا Whitespace نیستند.
  • انواع Whitespace، از جمله Whitespace انتهایی.

Space ابتدایی عمداً به کلمه بعدی متصل می‌ماند. در نتیجه، متن the cat به قطعه‌هایی شبیه the و cat تقسیم می‌شود، نه the، سپس و بعد cat. این تصمیم باعث می‌شود Tokenizer بتواند شکل کلمه در ابتدای متن را از شکل همان کلمه پس از Space متمایز کند.

Pattern بالا از قابلیت‌هایی مانند \p{L} استفاده می‌کند که در ماژول داخلی re در Python پشتیبانی کامل ندارند. برای اجرای مستقیم آن معمولاً از Package شخص ثالث regex استفاده می‌شود.

نمونه ساده:

import regex

PATTERN = regex.compile(
    r"'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+",
    flags=regex.IGNORECASE,
)

def pre_tokenize(text: str) -> list[str]:
    return PATTERN.findall(text)


print(pre_tokenize("I don't code in Python 3.11!"))

در این مثال، نام pre_tokenize و سایر نام‌های فنی انگلیسی باقی مانده‌اند، اما هدف Function روشن است: ایجاد Chunkهایی که BPE هرکدام را مستقل پردازش کند.

رویکرد SentencePiece

SentencePiece به‌جای وابستگی به Tokenization مخصوص یک زبان، متن را به‌صورت مستقیم و Language-independent پردازش می‌کند و معمولاً Space را با نشانه‌ای مانند ▁ نمایش می‌دهد. بسته به Model و تنظیمات، Normalization و تقسیمات داخلی خودش را نیز دارد؛ بنابراین درست نیست که در همه حالت‌ها آن را صرفاً «یک Byte stream بلند بدون هیچ مرحله مرزبندی» بدانیم.

مدل‌های مختلف خانواده Llama نیز دقیقاً یک Tokenizer یکسان ندارند. نسخه‌های قدیمی‌تر عمدتاً با SentencePiece شناخته می‌شوند، در حالی که Tokenizer مدل Llama 3 دارای Vocabulary و Pre-tokenization design متفاوتی است. پس هنگام پیاده‌سازی باید Configuration همان مدل هدف را بررسی و بازتولید کنید.

انتخاب روش Pre-tokenization مهم است:

  • محدودکردن Merge به Chunkها معمولاً Tokenهای قابل‌تفسیرتر و رفتار کنترل‌شده‌تری ایجاد می‌کند.
  • آزادی بیشتر برای Merge ممکن است در بعضی Corpusها Compression بهتری ایجاد کند.
  • Pattern نامناسب برای یک زبان می‌تواند باعث افزایش تعداد Token و هزینه پردازش شود.
  • هر تغییری در Pattern پس از Training، Token IDهای ورودی را تغییر می‌دهد و با مدل آموزش‌دیده ناسازگار است.

Special Tokenها

هر Tokenizer مناسب Production تعدادی Token ID را برای Markerهای ساختاری رزرو می‌کند:

Tokenکاربردنمونه مدل یا خانواده
[BOS] یا <s>مشخص‌کردن Beginning of sequenceLlama و برخی مدل‌های GPT-style
[EOS] یا </s>مشخص‌کردن End of sequenceبیشتر مدل‌های Generative
[PAD]Padding برای هم‌اندازه‌کردن Sequenceهای یک BatchBERT و T5 و بسیاری از Pipelineها
[UNK]نمایش Token ناشناخته؛ Byte-level BPE معمولاً به آن نیاز نداردBERT و WordPiece
<|im_start|>آغاز مرز یک Chat messageChatML-style templateها و برخی مدل‌ها مانند Qwen
<|im_end|>پایان مرز یک Chat messageChatML-style templateها و برخی مدل‌ها مانند Qwen
<|user|>Marker مربوط به نوبت User در بعضی Templateهابرخی مدل‌های Chat
<|assistant|>Marker مربوط به نوبت Assistant در بعضی Templateهابرخی مدل‌های Chat

نام و کاربرد دقیق Special Tokenها میان مدل‌ها متفاوت است؛ بنابراین جدول بالا نمونه‌ای مفهومی است و نباید بدون بررسی Configuration مدل هدف استفاده شود.

Special Tokenها نباید توسط BPE شکسته شوند. Pipeline معمولاً آن‌ها را با Exact match تشخیص می‌دهد، ID ثابتشان را ثبت می‌کند و فقط متن اطرافشان را به شکل عادی Tokenize می‌کند.

یک API مناسب باید مشخص کند آیا کاربر اجازه دارد Special Token را مستقیماً در متن وارد کند یا نه. برای مثال می‌توان Parameterهایی مانند allowed_special و disallowed_special داشت. این کنترل از آن جهت مهم است که متن غیرقابل‌اعتماد نتواند به‌سادگی Markerهای ساختاری Conversation را جعل کند.

طرح ساده مدیریت Special Token:

SPECIAL_TOKENS = {
    "<|bos|>": 50_000,
    "<|eos|>": 50_001,
    "<|pad|>": 50_002,
}

def encode_special(token: str) -> int:
    if token not in SPECIAL_TOKENS:
        raise ValueError(f"Unknown special token: {token}")
    return SPECIAL_TOKENS[token]

IDهای بالا صرفاً نمونه‌اند. در یک Tokenizer واقعی، هیچ ID نباید هم‌زمان هم به Token عادی و هم به Special Token اختصاص داده شود.

Chat Templateها

این بخش یکی از رایج‌ترین محل‌های سردرگمی و خطا در پیاده‌سازی Tokenizer است.

وقتی پیام‌هایی را به یک Chat model ارسال می‌کنید، API معمولاً فهرستی شبیه نمونه زیر دریافت می‌کند:

[
  {"role": "system", "content": "You are helpful."},
  {"role": "user", "content": "Hello"},
  {"role": "assistant", "content": "Hi there!"}
]

مدل این JSON را مستقیماً نمی‌بیند. Chat Template این ساختار را با استفاده از Special Tokenها، Role markerها، Newlineها و قواعد ثابت به یک متن تخت و سپس یک Token sequence تبدیل می‌کند. هر Model family قالب خاص خود را دارد.

نمونه مفهومی برای Llama 3:

<|begin_of_text|><|start_header_id|>system<|end_header_id|>

You are helpful.<|eot_id|><|start_header_id|>user<|end_header_id|>

Hello<|eot_id|><|start_header_id|>assistant<|end_header_id|>

Hi there!<|eot_id|>

نمونه ChatML-style که در متن اصلی با عنوان ChatGPT آمده بود:

<|im_start|>system
You are helpful.<|im_end|>
<|im_start|>user
Hello<|im_end|>
<|im_start|>assistant
Hi there!<|im_end|>

اگر Template اشتباه باشد، کیفیت خروجی مدل می‌تواند به‌شدت افت کند. مدل در زمان Training یک قالب مشخص دیده است و تغییراتی مانند حذف Newline، جابه‌جایی Marker، استفاده از Special Token اشتباه یا افزودن Space اضافی ممکن است ورودی را از الگوی Training distribution دور کند.

نکات مهم در پیاده‌سازی:

  • از Chat Template رسمی همان Model checkpoint استفاده کنید.
  • برای آغاز Generation معمولاً باید Assistant header را اضافه کنید، اما نباید پاسخ ساختگی Assistant را به ورودی بیفزایید.
  • مشخص کنید [BOS] و [EOS] را خود Template اضافه می‌کند یا encode؛ اضافه‌شدن دوباره آن‌ها خطاست.
  • Roleهای پشتیبانی‌شده مانند system، user، assistant و tool باید Validate شوند.
  • Template و Tokenizer باید Version هماهنگ داشته باشند.
  • با Golden test، خروجی Token IDها را با Reference implementation مقایسه کنید.

آموزش BPE روی Corpus

برای ساخت Vocabulary سفارشی، ابتدا متن‌های Training corpus را با همان Normalization و Pre-tokenization نهایی پردازش کنید. سپس:

  1. هر Chunk را به Byteهای اولیه تبدیل کنید.
  2. فراوانی تمام جفت‌های مجاور را محاسبه کنید.
  3. پرتکرارترین Pair را انتخاب و Merge کنید.
  4. یک Token جدید و Merge rule متناظر بسازید.
  5. مراحل ۲ تا ۴ را تا رسیدن به Vocabulary size موردنظر تکرار کنید.

Pseudo-code ساده:

def train_bpe(corpus: list[str], vocab_size: int):
    vocab = initialize_byte_vocab()  # 256 byte tokens
    sequences = prepare_sequences(corpus)
    merges = []

    while len(vocab) < vocab_size:
        pair_counts = count_adjacent_pairs(sequences)
        if not pair_counts:
            break

        best_pair = max(pair_counts, key=pair_counts.get)
        new_token = merge_pair(best_pair)
        sequences = apply_merge(sequences, best_pair, new_token)
        vocab.append(new_token)
        merges.append(best_pair)

    return vocab, merges

در پیاده‌سازی واقعی باید Frequency هر Chunk را نیز در نظر بگیرید؛ وگرنه تکرار یک کلمه در Corpus به‌درستی روی انتخاب Mergeها اثر نمی‌گذارد. همچنین نتیجه در حالت تساوی Pairها باید Deterministic باشد تا اجرای مجدد Training همان Vocabulary را تولید کند.

اعمال Mergeها در زمان Encode

در زمان Encode نباید دوباره فراوانی Pairها را محاسبه کنید. Merge ruleهای آموزش‌دیده دارای Rank هستند و Rule با Rank بهتر باید زودتر اعمال شود.

def encode_chunk(byte_tokens: list[bytes], merge_ranks: dict[tuple[bytes, bytes], int]):
    tokens = byte_tokens[:]

    while len(tokens) > 1:
        pairs = list(zip(tokens, tokens[1:]))
        ranked = [(merge_ranks[pair], pair) for pair in pairs if pair in merge_ranks]
        if not ranked:
            break

        _, best_pair = min(ranked)
        tokens = apply_merge(tokens, best_pair, b"".join(best_pair))

    return tokens

این نسخه برای آموزش مناسب است، اما به علت ساخت دوباره Pairها در هر Loop برای Production بهینه نیست. پیاده‌سازی‌های سریع‌تر از Data structureهای کارآمد، Cache و Code کامپایل‌شده استفاده می‌کنند.

ارزیابی Tokenizer

صرف اینکه یک Tokenizer بدون خطا Encode و Decode می‌کند، به معنی مناسب‌بودن آن نیست. دست‌کم معیارهای زیر را بررسی کنید:

Compression Ratio

یکی از تعریف‌های ساده:

compression_ratio = number_of_input_bytes / number_of_tokens

عدد بزرگ‌تر در این تعریف یعنی هر Token به‌طور متوسط Byteهای بیشتری را پوشش می‌دهد. می‌توانید معیار characters_per_token یا برعکس آن یعنی tokens_per_character را هم گزارش کنید، اما تعریف انتخابی باید در تمام مقایسه‌ها ثابت بماند.

نمونه مقایسه با tiktoken:

import tiktoken

def compression_ratio(text: str, token_ids: list[int]) -> float:
    if not token_ids:
        return 0.0
    return len(text.encode("utf-8")) / len(token_ids)


encoding = tiktoken.get_encoding("cl100k_base")
reference_ids = encoding.encode(text)
custom_ids = tokenizer.encode(text)

print("tiktoken:", compression_ratio(text, reference_ids))
print("custom:", compression_ratio(text, custom_ids))

مقایسه را فقط روی انگلیسی انجام ندهید. Dataset ارزیابی بهتر است شامل موارد زیر باشد:

  • انگلیسی رسمی و محاوره‌ای؛
  • فارسی و عربی، به‌ویژه متن RTL؛
  • زبان‌های CJK؛
  • Emoji و ترکیب Emoji با Skin tone یا Zero-width joiner؛
  • Python، JavaScript، JSON و Shell code؛
  • URL، Email، Number و تاریخ؛
  • Whitespaceهای خاص، Tab و چند Newline؛
  • متن‌های خارج از Domain اصلی Training.

معیارهای تکمیلی

  • Round-trip correctness: آیا decode(encode(text)) مطابق قرارداد است؟
  • Unknown rate: در Byte-level BPE باید عملاً صفر باشد.
  • Fertility: هر کلمه به‌طور میانگین به چند Token شکسته می‌شود؟
  • Sequence length distribution: طول Sequenceها در Percentileهای مختلف چقدر است؟
  • Cross-language fairness: آیا یک زبان برای محتوای هم‌اندازه چند برابر زبان دیگر Token مصرف می‌کند؟
  • Speed و memory: Throughput و Peak memory در Encode و Decode چقدر است؟
  • Reference compatibility: آیا Token IDها و Special Tokenها با مدل هدف دقیقاً هماهنگ‌اند؟

سرعت

Python خالص معمولاً برای Tokenization در مقیاس Production کافی نیست.

tiktoken متعلق به OpenAI با Rust پیاده‌سازی شده و Python binding دارد. کتابخانه Hugging Face tokenizers نیز از Rust استفاده می‌کند و SentencePiece با C++ پیاده‌سازی شده است. بسته به داده، Hardware، Batch size و نحوه Benchmark، این ابزارها می‌توانند ده‌ها برابر سریع‌تر از پیاده‌سازی ساده Python باشند.

برای درک مقیاس، اگر Tokenize کردن ۱۵ تریلیون Token با سرعت یک میلیون Token در ثانیه انجام شود:

15,000,000,000,000 / 1,000,000 = 15,000,000 seconds ≈ 174 days

اگر Throughput به صد میلیون Token در ثانیه برسد:

15,000,000,000,000 / 100,000,000 = 150,000 seconds ≈ 1.7 days

این محاسبه فقط برای نشان‌دادن مقیاس است. در عمل، Tokenization می‌تواند به‌صورت موازی و در کنار خواندن، Sharding و ذخیره Dataset انجام شود و سرعت واقعی به کل Data pipeline وابسته است.

هدف از ساخت Tokenizer با Python، فهم دقیق Algorithm و اجزای Pipeline است. در Production بهتر است از یک پیاده‌سازی کامپایل‌شده استفاده کنید و Python را به Wrapper، Configuration، Training orchestration و Test محدود نگه دارید.

خطاهای رایج

  • استفاده از Normalization متفاوت در Training و Inference.
  • Decode کردن هر Byte token به‌صورت مستقل؛ یک Unicode character ممکن است از چند Byte تشکیل شده باشد و باید پس از بازسازی کل Byte stream Decode شود.
  • شکستن Special Token توسط Regex یا BPE.
  • افزودن دوباره [BOS] یا [EOS] هم در Chat Template و هم در encode.
  • تغییر ترتیب Merge ruleها یا نادیده‌گرفتن Rank آن‌ها.
  • آموزش روی Corpus نامتوازن و ایجاد Tokenization بسیار پرهزینه برای زبان‌های کم‌نماینده.
  • مقایسه Compression Ratio با تعریف‌های متفاوت.
  • اعتماد به Testهای انگلیسی و نادیده‌گرفتن Unicode edge caseها.
  • استفاده از Python loopهای تو در تو روی Dataset بزرگ بدون Profiling.

جمع‌بندی

یک Tokenizer کامل از کنار هم قرارگرفتن چند تصمیم دقیق ساخته می‌شود: Byte-level representation تضمین می‌کند ورودی ناشناخته نداشته باشیم؛ Normalization تنوع نوشتاری را طبق سیاست پروژه کنترل می‌کند؛ Pre-tokenization مرزهای مجاز Merge را تعیین می‌کند؛ BPE الگوهای پرتکرار را به Tokenهای فشرده تبدیل می‌کند؛ Special Tokenها و Chat Template ساختار مورد انتظار مدل را می‌سازند؛ و ID Mapping خروجی نهایی قابل استفاده برای مدل را تولید می‌کند.

پیاده‌سازی Python برای یادگیری این سازوکار بسیار ارزشمند است، اما Tokenizer مناسب Production علاوه بر صحت Algorithm به سازگاری دقیق با مدل، Versioning، Testهای چندزبانه، امنیت Special Tokenها و Performance بالا نیاز دارد.
